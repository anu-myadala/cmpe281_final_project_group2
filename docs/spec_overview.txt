Overview of the Component Designs
This document is Deliverable #2 of Group 2: the component design of the Smart Car Intelligent Cloud Platform (SCICP). It
takes the system design of Deliverable #1 as fixed (components, REST APIs, data stores, roles, and alert states) and gives each
component its detailed design in the five sections of the component design template: component overview, application interface
design, function, data and behavior design, business logic, and graphic user interface design. Each team member wrote the part
for the component they will build, as Deliverable #1 assigned them. Figures and tables are numbered through the whole
document; section numbers restart in each part, so "Section 4.1" in a part refers to that part.

The shared conventions are defined once, in Part I, and the other parts follow them: every public endpoint is under /api/v1
with a bearer JWT whose role and tenant come from the token; errors use one envelope and the codes of Table 8; internal calls
between containers go to /internal/... with a service token; components never write each other's tables and read them only
through the SELECT-only access of the C5 data layer; live updates go through the EventBus and the WebSocket hub of Part I;
and MQTT topics live under scicp/v1/. Objects live in two S3 buckets in us-west-2: scicp-clips for the audio clips (key layout
in Part II) and scicp-models for the model artifacts (Part I). All parts use the same seed data: Tenant A (tA, the Nguyen
household, car AV-01), Tenant B (tB, Bay Shuttle LLC, cars AV-10 to AV-14), the model sound-classifier with version 1.1.0
active and 1.2.0 registered, and the sample alert 20482.

Part II, Part III

A few details were aligned when the parts were combined, and each part now states them the same way. The model activation
message is published on the MQTT topic above as well as on the EventBus, because the classifier worker runs in its own
container and cannot receive in-process events. The tenant table carries a time_zone column, in which C3 evaluates quiet hours.
The by field of alert.updated is the display name of the user who acted. The device.status message carries the optional muted and
config fields that the C2 device editor needs. The tenant list of the administration API is readable by the two other staff roles so
that their pages can offer a tenant selector. Each part keeps the ERD of the tables it owns: Part I the tenant, user, subscription,
and registry tables, Part II the vehicle, device, command, network, and clip tables, Part III the alert tables and the MongoDB
collections; together they are the Deliverable #1 ERD with the columns each part adds.
