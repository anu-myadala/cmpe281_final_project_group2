Part I. C1 Cloud Platform Dashboard and System Admin
Component owner: Anukrithi Myadala (anukrithi.myadala@sjsu.edu). Includes the C4 model registry pages and APIs.

1. Component Overview
This part is the detailed design of component C1, the Cloud Platform Dashboard and System Admin of the Smart Car Intelligent
Cloud Platform (SCICP), together with the C4 model registry pages and APIs that the same author builds. It is task T7 of the
schedule in our Deliverable #1 (its Table 19) and keeps the system design of that document [1] unchanged (component
boundaries, the REST and WebSocket APIs of its Table 9, the MySQL and MongoDB schemas, the role-based views), filling in
what is inside C1: from the black-box view of the component to its white-box design [2].

1.1 Purpose
C1 is the single web entry point of the platform. Every user, whatever the role, signs in through C1, and C1 decides which view
that role sees. For car owners and fleet managers it shows what is happening to their cars: vehicles, open alerts, recent event
counts, and the subscriptions that decide who is notified. For service staff it shows statistics across tenants and produces CSV
reports. For the system administrator it manages tenants, users, roles, and the platform-wide alert types. Through the C4 registry
pages it lets staff register a classifier version with its file and held-out test results, choose the active version, roll back, and export
feedback labels for retraining. C1 does not create alerts, does not talk to cars, and does not run inference; those are C3, C2, and
the C4 worker. Figure 1 places C1 among the other components, the users, and the AWS services it depends on, and labels every
arrow with the interface it uses. As in Deliverable #1, we design C1 for the full-scale platform (four portals behind CloudFront
and an Application Load Balancer, WebSocket rooms in Redis, separate services per component) and build what the demo
needs (one React application and one FastAPI service on one EC2 instance with an in-process event bus); the APIs, tables,
classes, and rules are the same in both.

2. Component Application Interface Design and Analysis
Sections 2.1 to 2.6 specify the REST APIs of the six API groups, 2.7 the WebSocket connectivity API, 2.8 the internal interfaces
to the other components and AWS services, and 2.9 who may call what and how the APIs are versioned and protected. Every C1
and registry endpoint of Table 9 of Deliverable #1 is here; this design adds the session endpoints (/auth/refresh, /auth/logout,
/auth/me, /auth/password/change), GET /intelligence-services, the admin list, reset-password, and design-only audit calls, and
the registry versions, complete, rollback, download, feedback, and feedback export calls; PUT /subscriptions becomes PUT
/subscriptions/{vehicleId} and the alert-type calls become GET, PUT /admin/alert-types/{code} because the six codes are
fixed. The business rules BR-01 to BR-12 are stated in Section 4.
Conventions. All endpoints are under /api/v1 and exchange JSON; dates are ISO 8601 in UTC. Every request except login
carries Authorization: Bearer <accessToken>; the access token is a JWT [4] (HS256, 15 minutes) with the claims sub,
tenantId, role, plan, name, and jti, and the tenant of a request always comes from the token, never from the URL (Deliverable #1,
Section 3.3). Staff roles, which have no tenant, pass tenantId as a query parameter where a tenant scope is needed;
TenantContext validates it, and tenant roles may pass it but it is ignored (BR-03). Errors use one envelope, {error: {code,
message, details?}}, with the codes of Table 8; a business-rule refusal puts the rule id in details.rule and the failing
field next to it so that the page can show the error inline. Bodies are Pydantic models validated by FastAPI, which publishes the
OpenAPI [6] document our Postman tests and the C2 and C3 teams use. vehicleId is the public vehicle code (AV-01), the
MongoDB tenantId is the tenant code (tA, tB) stored in tenant.code, and eventRef is the 24-character ObjectId of the audio
event. In the tables a question mark marks an optional field, vertical bars an enumeration, and the last column names the rule
enforced and the audit action written.

Live updates reach the browser over one WebSocket [5] at /ws (M2), proxied by nginx as WSS; the client sends the JWT in its
first message, the server verifies it (close code 4401 if invalid), joins the connection to its rooms, and from then on only sends the
messages of Table 15: the three events of Deliverable #1 (alert.created, alert.updated, device.status) plus model.activated and
the heartbeat pair that this design adds. Rooms are decided once from the verified claims (a tenant role joins tenant:{tenantId}
only, a staff role joins staff) and no message carries a tenant id the client could change (O4). The server pings every 30 s; after
three missed pings (90 s) WsClient closes the socket, retries with back-off from 2 s to 30 s, polls GET /dashboard/overview
every 10 s, and shows the yellow LiveBanner until the socket is back and one overview reload catches up.

Section 3 is the white-box design of C1, drawn in UML 2.5 [3]: 3.1 the classes of the back end and the front end, 3.2 the

3.1 Logic design
The back end is one FastAPI module per component inside one service (Deliverable #1, Section 3.4); C1 is the package app/c1
and the registry pages are app/c4registry, with SQLAlchemy and Motor as drivers, Pydantic for validation, argon2 for

3.2.1 Pseudocode of the rule-carrying functions
AuthService.login implements the decision table of Section 4.1; the lock check comes before the password check so that a

locked account does not leak whether the password was right, and the counters live on the app_user row so the lock survives a
restart.
def login(email, password, ip):
user = UserRepo.find_by_email(email)
if user is None or user.status == DISABLED: raise Unauthorized()

# generic 401 (R1, BR-02)

if user.tenant_id is not None and TenantRepo.get(user.tenant_id).status == SUSPENDED:
raise Forbidden("TENANT_SUSPENDED")

# R2

if LoginThrottle.is_locked(user): raise Locked(locked_until=user.locked_until)

# R3

if not PasswordHasher.verify(password, user.password_hash):
locked = LoginThrottle.record_failure(user)

# R4 / R5: 5 in 15 min -> lock 15 min

AuditLogger.write(user, user.tenant_id, "LOGIN_LOCK" if locked else "LOGIN_FAIL",
"app_user", user.user_id, None, {"failed": user.failed_logins, "ip": ip})
raise Locked(locked_until=user.locked_until) if locked else Unauthorized()
LoginThrottle.reset(user)

# R6

user.last_login_at = now(); UserRepo.save(user)
pair = TokenService.issue(user)
AuditLogger.write(user, user.tenant_id, "LOGIN", "app_user", user.user_id, None, {"ip": ip})
return pair, user.must_change_password

ModelRegistryService.activate is the transaction of Section 4.6. The current ACTIVE row is locked with SELECT ...
FOR UPDATE (InnoDB locking reads [9]) before the target is read, which guarantees at most one ACTIVE version per model

5. Component Graphic User Interface Design
The user interface is the dashboard shell that all four views share plus the pages of the owner view (overview, vehicle map,
vehicles, subscriptions, reports), the staff statistics and reports, the administration pages, and the AI model pages: 5.1 gives the
style rules, 5.2 the function partition tree, 5.3 the storyboards, 5.4 the UI markup diagram, and 5.5 the page templates with the
APIs behind each one; the alert and device pages are drawn in the C3 and C2 designs.

5.1 GUI style
Table 32 lists the rules every page follows, from the Deliverable #1 dashboard architecture and the Material UI defaults [8] (13–
14 px body, 17 px titles, 24 px KPI numbers, 12 px tables with sticky headers; focus in reading order, dialogs trap focus and
close with Esc, ARIA labels, WCAG AA contrast); the wireframes of all three parts are drawn with the same shell, palette, and
type, and use the two seeded tenants and the seven sound classes.

Element

Rule

Layout

One shell for every role: 200 px left menu filtered by role, 52 px top bar (page title, tenant selector for staff roles, global
search, live indicator, open-alert badge, user menu), content area on a 12-column grid of cards; menu collapses to icons
below 1024 px, grid to one column below 768 px

Color

Severity chips CRITICAL red, HIGH orange, MEDIUM yellow, LOW gray; device status ONLINE green, OFFLINE
amber, FAULT red, PROVISIONING and REGISTERED gray, DISABLED gray with strike-through (Part II); alert

is listed without a position because it has never sent telemetry) → click AV-11 → its detail opens on the right and the trail of its

email, name, role FLEET_MANAGER → Send → toast "Invitation sent" → SES email with a temporary password → first
login → change-password dialog → the owner view of Tenant C opens. Staff activates a version: AI models → select 1.3.0
(held-out macro-F1 0.87) → Set as active → confirm dialog "Active now 1.1.0 (macro-F1 0.84) → becomes INACTIVE; Target
1.3.0 (macro-F1 0.87), BR-10 passes" → Activate → toast "Version 1.3.0 is active" → the ACTIVE chip moves and the
classifier worker reloads within a few seconds, visible on the next alert detail, which prints the model version.
