Part II. C2 Edge Agent and IoT Device Management
Component owner: Brandon Rivera Venegas (brandon.riveravenegas@sjsu.edu). Includes per-car data management and the
edge agent.

1. Component Overview
This part is the detailed design of component C2, Edge Agent and IoT Device Management, of the Smart Car Intelligent Cloud
Platform (SCICP). It covers the cloud side of C2 (vehicles, IoT devices, provisioning, device configuration and control, device
status, Wi-Fi settings, and per-car data management) and the edge agent and car simulator that act as the cars. It is task T7 of our
Deliverable #1 [1] and keeps that system design unchanged: the component boundaries, the C2 REST APIs of its Table 9, the
MQTT topics of its Table 14, the device states, and the vehicle and device tables of its ERD. It fills in what is inside C2 and fixes
the interfaces that Part I [2] and Part III [3] already rely on: GET /internal/clips/{clipId}, the audio event format, the
device.status event, the vehicle list for the overview, and the vehicle limit.

1.1 Purpose
C2 is the part of the platform that knows the cars. An IoT engineer registers a vehicle and its devices (interior and exterior
microphones, cameras, and the edge gateway that runs the agent), provisions the vehicle so that its agent gets its own MQTT
login and upload token, changes a device setting such as the microphone gain, and watches whether each device is online. C2
sends every setting and command to the car over MQTT and shows it as confirmed only when the car says it applied it. C2 also
receives the 5 s audio clips that the cars upload, stores them in S3, serves them to the classifier worker, and lets owners and
engineers list, play, and delete the clips of each car and set how long they are kept.
The edge agent is the other half. It is one Python program that runs on a laptop with its built-in microphone as the live car, or
many times as simulated cars that replay the course datasets. It listens, cuts a clip when a pre-filter finds a candidate sound,
uploads the clip to C2, publishes the audio event over MQTT, sends telemetry every 10 s, and applies the settings and
commands it receives. C2 does not classify sounds, does not create alerts, and does not draw the dashboard shell; those belong to
the C4 worker and C3 [3] and to C1 [2]. Figure 22 places C2 among its neighbors. As in Deliverable #1, we design for the fullscale platform (AWS IoT Core things with X.509 certificates, device shadows, pre-signed uploads, Redis for the event bus) and
build what the demo needs (Mosquitto with one login per car, a multipart upload to the API, an in-process event bus, one EC2
instance); the APIs, tables, classes, and rules are the same in both.

2. Component Application Interface Design and Analysis
Sections 2.1 to 2.5 specify the REST APIs of C2 (vehicles and riders, devices, provisioning and commands, network, clips and
per-car data), 2.6 the error cases, 2.7 the internal API, 2.8 the MQTT connectivity API between the cars and the platform, 2.9 the
events C2 publishes, and 2.10 who may call what and how the APIs are protected. Every C2 endpoint of Table 9 of Deliverable
#1 is here; this design adds GET and PUT on one vehicle's network, the command history and command status, the playback
URL, the riders calls, GET /vehicles/{id}/telemetry, and the internal clip call. The business rules BR-C2-01 to BR-C2-26 are
stated in Section 4.
Conventions. C2 follows the conventions of the C1 design [2]: all endpoints are under /api/v1 and exchange JSON, dates are
ISO 8601 in UTC, every request carries a bearer token, and the tenant of a request comes from the token, never from the URL;
staff roles, which have no tenant, pass tenantId as a query parameter, and TenantContext validates it (BR-C2-01). vehicleId is
the public vehicle code (AV-01), deviceId the public device code (dev-0112), tenantId in MQTT topics and MongoDB the
tenant code (tA), and clipId 8 lowercase hexadecimal characters. Errors use the envelope {error: {code, message, details?}} and
the codes of Table 8 in Part I; C2 adds four: GONE 410 when a clip was deleted or expired, PAYLOAD_TOO_LARGE 413 and
UNSUPPORTED_MEDIA 415 for clip uploads, and NOT_IMPLEMENTED 501 for the design-only commands. A refused
rule is BUSINESS_RULE 422 with details.rule set to the BR-C2 id and details.field next to it. Calls that need the car to act
(settings, commands, network) answer 202 Accepted with a commandId, because the result arrives later over MQTT. Lists are
paged with page and size (default 25, maximum 100). In the tables a question mark marks an optional field and vertical bars an
enumeration.

Security. Users authenticate with the C1 JWT (HS256, 15 minutes). The device token is a JWT [8] signed with a separate key,
with the claims role DEVICE, tenantId, vehicleId, ver (the vehicle's credential_version), and an expiry of 180 days; it is
accepted only by POST /ingest/clips and is refused as soon as the vehicle is rotated or retired (BR-C2-09). The service token is
the one of the C3 design. MQTT passwords are 24 random URL-safe characters; Wi-Fi passwords are encrypted with Fernet
(AES-128-CBC with HMAC) under a key from the environment (SecretBox) and are sent to a car only inside its TLS
connection. Rate limits: the 60 requests per minute per user of the C1 design, and 12 clips per minute per car. Versioning: the
URL prefix /api/v1 and the MQTT prefix scicp/v1 change together; added optional fields do not change the version, and the
agent ignores unknown fields.

3.3.3 Object storage and secrets
Clips are stored in the scicp-clips bucket under
tenants/{tenantId}/vehicles/{vehicleId}/YYYY/MM/DD/{clipId}.wav, the key format that the C1 and C3

designs already use. The date is the capture date in UTC, so the daily retention job and a manual cleanup can work by prefix.
Objects are private; the browser plays them through a presigned GET [9] that is valid for 15 minutes, and the worker reads
them through C2. An S3 lifecycle rule deletes any clip object older than 400 days as a backstop in case a job run is missed. A
5 s mono 16 kHz WAV is about 160 KB; at our scale (one live car and ten simulated cars uploading one clip a minute during
work sessions) this is well under 1 GB for the semester.
Secrets. The MQTT passwords live only in Mosquitto's dynamic-security.json as salted PBKDF2 hashes; C2 keeps the
username and the credential version. The device-token signing key, the SecretBox key for Wi-Fi passwords, and the dynamic
security admin password come from the instance's .env file, which is not in Git; in the full design they move to AWS Secrets
Manager (Deliverable #1, Table 6).

5.1 GUI style
Table 71 gives the style rules shared by all C2 pages. They extend the shell style of the C1 design (left menu, top bar, cards,

Element

Rule

Layout

C1 shell; the Vehicle and device manager is a two-column page: vehicle list (fixed 260 px) on the left, vehicle detail

Status chips

ONLINE green, OFFLINE amber, FAULT red, PROVISIONING and REGISTERED gray, DISABLED gray with

Settings state

Confirmed values in normal text with a check mark and time; pending values in an amber chip "v4 SENT hh:mm:ss"

Retire, Delete device, Delete clip, and Rotate open a confirmation dialog that names the object (for example "Retire
