Part III. C3 Alert Tracking and Monitoring
Component owner: Ray Zhao (ray.zhao@sjsu.edu). Includes the C4 classifier worker and the MongoDB collections.

1. Component Overview
This part is the detailed design of component C3, Alert Tracking and Monitoring, of the Smart Car Intelligent Cloud Platform
(SCICP), together with the C4 classifier worker that produces the results C3 consumes and the MongoDB collections that hold
the sound events. It is task T7 of Table 19 of our Deliverable #1 [1] and keeps that system design unchanged (component
boundaries, the REST APIs of its Table 9, the MySQL and MongoDB schemas, the alert states), filling in what is inside C3 and
the worker. The model registry pages and the feedback API belong to C1 [2]; the vehicle, device and clip upload belong to C2.

1.1 Purpose
C3 decides when a classified sound becomes an alert, records what happens to the alert until it is closed, and tells the right
people. For every result the worker reports, C3 applies the alert rules of the tenant to the top classes and the vehicle state, checks
the owner's subscription, creates at most one alert, and sends it to the dashboards over the event bus and to the owner and riders
by email. Owners, fleet managers, service staff and riders then list the alerts, play the clip, and acknowledge, resolve, or mark a
false alarm; every action is stored with the user and time.
The classifier worker is the other half of that path. It receives the audio event from the car over MQTT, fetches the clip,
computes a CLAP embedding, classifies it into the seven semester classes with a small head, writes the event to MongoDB, and
reports the result to C3. C3 does not talk to cars, does not change classes or models, and does not draw the dashboard shell; those
belong to C2, C1 and the registry in C1. Figure 35 places C3 and the worker among their neighbors. As in Deliverable #1, we
design for the full-scale platform (an SQS queue and an inference group per tenant size, IoT Core, Redis pub/sub) and build
what the demo needs (one worker container, Mosquitto, one FastAPI service with an in-process event bus on one EC2 instance);
the APIs, tables, classes and rules are the same in both.

2. Component Application Interface Design and Analysis
Sections 2.1 to 2.3 specify the REST APIs of C3 (alerts, alert rules, and the internal result call), 2.4 the interfaces of the classifier
worker, 2.5 the events and WebSocket messages C3 produces, 2.6 the internal interfaces, and 2.7 who may call what and how
the APIs are versioned and protected. Every C3 endpoint of Table 9 of Deliverable #1 is here; this design adds GET /alerts/map,
DELETE /alert-rules/{ruleId}, the internal result call in full, the worker interfaces, and the model topic. The business rules BRC3-01 to BR-C3-14 are stated in Section 4.
Conventions. C3 follows the conventions of the C1 design [2]: all endpoints are under /api/v1 and exchange JSON, dates are
ISO 8601 in UTC, every request except login carries a bearer JWT, and the tenant of a request comes from the token, never from
the URL; staff roles pass tenantId as a query parameter where a tenant scope is needed. vehicleId is the public vehicle code (AV01), the MongoDB tenantId is the tenant code (tA, tB), and eventRef is the 24-character ObjectId of the audio event. Errors use
the one envelope and the codes of Table 8 in Part I; C3 adds two details: a refused transition is CONFLICT 409 with details
{from, to, allowed[]}, and a refused rule value is BUSINESS_RULE 422 with details.rule set to the BR-C3 id. Lists are paged
with page and size (default 25, maximum 100); limit is accepted as an alias of size so that C1's AlertClient works unchanged.

2.1 Alerts
Table 83 is the API of M3 and M2. The queue and the detail are read-only; the one write is the action, which changes the status

within the 300 ms budget: the event, the rule that fired, a presigned clip URL (15 minutes), the action history and the notification

2.3 Internal result call
Table 85 is the one call between the worker and C3. The worker has already inserted the audio event, so the call carries only
what C3 needs to decide; C3 answers with the decision and also writes it into the event (decision.alert, decision.alertId,
decision.alertType). The call is idempotent: a repeated result for the same event returns the first decision because (event_ref,
alert_type_code) is unique, which makes the QoS 1 redelivery of MQTT harmless (BR-C3-12). It uses a service token (role
SERVICE, HS256, 24 hours), and nginx does not route /internal/ from the Internet, so only containers on the Docker network
can reach it.

C1's AlertClient calls GET /alerts and GET /alerts/{alertId} with the service token, which RbacGuard treats as the staff scope.
Versioning: the prefix /api/v1 is the version, fields are only added within v1, and a breaking change would add /api/v2 beside it.
Pagination: GET /alerts is paged with a total; the map is bounded to 500 points by design. Idempotency: GET, PUT and

3.2.1 Pseudocode of the rule-carrying functions
AlertEngine.evaluate decides, create_alert writes. The two are separate so that the decision can be unit-tested without a
database, and so that the write is one transaction.
def evaluate(event, result):

# BR-C3-01 .. BR-C3-06

if result.error:
return store_decision(event, alert=False, reason='ERROR_RECORDED')
state = RuleResolver.state_of(event.context)

# MOVING or PARKED

candidates, first_reason = [], None
for score in result.topK[:3]:

# highest confidence first

rule = RuleResolver.find_rule(event.tenant, score.cls, state)
if rule is None or not rule.enabled:
first_reason = first_reason or reason_for(score.cls, state)

# NO_RULE or STATE_MISMATCH

continue
if score.conf < rule.min_confidence:
first_reason = first_reason or 'BELOW_THRESHOLD'; continue
sub = SubscriptionRepo.get(event.vehicle, rule.alert_type)
if sub is None or not sub.enabled:
first_reason = first_reason or 'SERVICE_OFF'; continue
if rule.min_repeats > 1 and RuleResolver.repeats(event.vehicle, score.cls,
rule.window_s) < rule.min_repeats:
first_reason = first_reason or 'REPEAT_PENDING'; continue
candidates.append(Candidate(severity_of(rule), score, rule, sub))
if not candidates:
return store_decision(event, alert=False, reason=first_reason or 'NO_RULE')
best = max(candidates, key=lambda c: (RANK[c.severity], c.score.conf))
return create_alert(event, best)

3.2.2 Training pipeline
The offline pipeline of task T12 produces the head that the worker serves. Its one design decision matters for the numbers we
report: the split is by original recording. The notebooks we were given split the files after augmentation, so noisy or pitch-shifted
copies of one recording can land in both the training and the test set, which makes their 96 to 97 percent accuracy figures
optimistic; we use them as baselines and re-measure on a split that cannot leak.
clips = DatasetBuilder.collect(DRIVE_FOLDERS)

# 7 class folders; every clip keeps origin_id of its

source recording
train, val, test = GroupedSplitter.split(clips, group='origin_id', ratio=(0.70, 0.15, 0.15),
stratify='label', seed=42)
emb = {c.id: ClapEncoder.embed(resample(c.audio, 48000)) for c in clips}
head = Head(512, 128, 7)

# backbone frozen

# linear, ReLU, dropout 0.3, linear

fit(head, train, emb, loss='cross_entropy', class_weights=balanced(train), early_stop='val macro-F1')
report = Evaluator.report(head, test)
hints

# precision, recall, F1 per class, macro-F1, confusion matrix

= {cls: lowest_conf_with_precision(head, val, cls,

target=0.90) for cls in ALERT_CLASSES}

# seeds min_confidence

ModelExporter.write(head, classes=CLASSES, metrics=report,
hints=hints)

3.3.3 Object storage and retention
Clips live under tenants/{tenantId}/vehicles/{vehicleId}/YYYY/MM/DD/{clipId}.wav in the scicp-clips bucket, written by
C2 and read by C3 only through StorageClient.presign_get with a 15 minute URL; before signing, AlertService checks that
the key starts with the tenant prefix of the alert's own tenant, so a wrong event reference cannot expose another tenant's clip,
and that the clip row of Part II is still STORED (SELECT-only on clip), so a clip the owner deleted or the retention job
removed shows as no longer available instead of a broken link. The worker reads model artifacts from
models/{modelId}/{version}/model.pt. When an audio event expires, the TTL index removes the document, the alert rows
stay (they hold the class, confidence and model version), and the detail page shows that the event has expired and offers no
clip. Alert rows are kept for the semester; the full design archives them after 12 months. The nightly MySQL and MongoDB
dumps to S3 of C5 cover all of the tables and collections above.
